# Core Features

1. **Player Search** — search PUBG players via the official PUBG Developer API.
2. **Match Analytics** — kills, damage, survival time, placement, headshot rate, win rate.
3. **AI Insights** — Performance Summary, Strengths, Weaknesses, Recommendations, generated by Gemini from processed metrics (never raw telemetry).
4. **Analysis History** — store historical analysis.
5. **Analytics Dashboard** — trends from historical data.

## AWS environment: Learner Lab, not a personal account

Deployment target is an RMIT-provided AWS Academy Learner Lab (see `PROJECT_CONTEXT.md` → AWS Environment). This means: use the Lab's pre-provisioned role (`LabRole`/`LabInstanceProfile`) for service execution roles — never design around creating custom IAM roles/policies, Learner Lab doesn't allow it. Also expect compute to stop between sessions and need restarting; Elastic Beanstalk's stable URL means this doesn't require reconfiguration, just a restart.

## Automation is graded, manual setup is not

The rubric only awards points for a service if it is "fully implemented and automated" and "automatically invoked by your client interface operations/code/other services **other than CLI/AWS Console**." A service that only works because someone clicked through the AWS Console once scores **zero** for that line, no matter how well it works in the demo.

Practical rule: every AWS interaction must be reachable through application code — a user action or backend process triggers an AWS SDK call. Manual console configuration is fine for one-time infrastructure setup (creating a bucket, a table, a function shell) but the *runtime behavior* the demo relies on must be code-driven, not a manual step repeated for the examiner.

## Third-party API budget: exactly two

**PUBG Developer API** and **Google Gemini API**. The rubric only grades two third-party API integrations even if more are added — do not introduce a third graded external API. If a feature seems to need another external service, ask the user before adding it.

# Backend Package Structure — feature-based, not layer-based

`com.pubginsight` is organized by **feature**, not by technical layer. Do not create top-level `controller/`, `service/`, `dto/`, `mapper/` packages for application features — that was the original structure and was deliberately replaced.

- `client/<provider>/` — external API integrations shared across features (e.g. `client/pubg/`, `client/gemini/`). Each owns its own wire-format DTOs (`client/pubg/dto/`), its own config properties, and its own exception type for that integration's failures. A client should never depend on a feature-specific exception — if a feature needs a different error for "not found" vs "call failed," translate it in the feature's service layer, not in the client.
- `common/` — cross-cutting concerns used by everything: `common/config/` (e.g. `CorsConfig`), `common/exception/` (e.g. `GlobalExceptionHandler`).
- `<feature>/` (e.g. `player/`, and later `match/`, `insight/`, `history/`, `dashboard/`) — one package per core feature (see Core Features below), containing that feature's own Controller, Service, DTO, Mapper, and exceptions. Everything a feature needs to work lives together; nothing is scattered across generic layer folders.
- A tiny standalone concern like the health check gets its own small package (`health/`) rather than living in a generic `controller/`.

When starting a new feature, create its package and put the DTO → Client-usage → Service → Controller pieces inside it, following the implementation order below — just don't scatter them into cross-feature layer folders.

# Before Writing Code

Always ask yourself

1. Does this belong in the backend or frontend?
2. Does this violate separation of concerns?
3. Is there already an existing implementation — verified by reading the actual source, not by trusting "Completed" claims in `TASK.md`/`PROJECT_CONTEXT.md`? Those docs have previously claimed a working health endpoint and FE↔BE connection that didn't exist in code.
4. Can this be reused?
5. Does this stay within the approved AWS services and third-party API budget?
6. Will the AWS interaction be automated (code-triggered), not a manual Console step?
7. Does a written deliverable (architecture diagram, report section) need updating alongside this change?

# AI Integration Principles

Gemini is an assistant. Gemini is NOT the business logic.

Backend computes gameplay metrics. Gemini only converts structured metrics into natural language insights.

Example

Backend

```
Average Damage = 520
KD = 2.1
Headshot Rate = 21%
```

↓

Gemini

```
Strengths
Weaknesses
Recommendations
```

Never send unnecessary data to Gemini.
